# Спецификация: SMS-коммуникация в PaNa CRM

Статус: Draft for estimation  
Версия: 1.1  
Дата обновления: 2026-10-01

## 1. Назначение

Реализовать в PaNa CRM историю SMS-коммуникаций и отправку сообщений из карточки пациента/обращения. Решение не должно зависеть от одного оператора: SMSAPI, SuperVoIP и последующие провайдеры подключаются через сменные адаптеры без переработки интерфейса, бизнес-процессов и основной модели данных CRM.

## 2. Бизнес-проблема и цель

Сейчас SMS-коммуникация находится вне единого профиля пациента. Оператор не видит полной истории контактов, не может отправить произвольное сообщение из CRM, а автоматизации и задачи не получают подтверждённый факт отправки.

Целевой результат:

- оператор отправляет SMS непосредственно из карточки пациента или кейса;
- каждое сообщение фиксируется как отдельное взаимодействие;
- история сохраняется в профиле пациента и связана с кейсом и, при наличии, задачей;
- администратор настраивает тексты и провайдера без изменения кода пользовательского интерфейса;
- переход с SMSAPI на SuperVoIP или другого провайдера не требует миграции бизнес-сущностей;
- на третьем этапе CRM поддерживает двустороннюю переписку.

## 3. Термины

| Термин | Определение |
|---|---|
| Пациент | Единый профиль человека в CRM, объединяющий контакты, кейсы, задачи и коммуникации. |
| Кейс | Отдельный процесс взаимодействия с пациентом, связанный с услугой, клиникой и воронкой. |
| SMS Message | Входящее или исходящее SMS, сохранённое как самостоятельная сущность. |
| SMS Provider | Внешний сервис доставки и/или приёма SMS. |
| Provider Adapter | Изолированный модуль, преобразующий единую модель CRM в API конкретного провайдера и обратно. |
| Шаблон | Управляемый администратором текст с переменными CRM. |
| Conversation Thread | Последовательность входящих и исходящих сообщений с одним пациентом/номером. |

## 4. Архитектурное решение

### 4.1. Основной принцип

Пользовательский интерфейс, карточка пациента, кейсы, задачи, workflow и шаблоны не обращаются к API SMSAPI или SuperVoIP напрямую. Все операции выполняются через внутренний `SMS Service`.

```text
Patient / Case / Task / Automation
                |
           SMS Service
                |
       Provider Adapter Layer
        /          |          \
   SMSAPI     SuperVoIP     Custom
```

Frappe `send_sms` hook может использоваться как техническая точка входа, но провайдерская логика, входящие webhook, нормализация статусов, идемпотентность и привязка сообщений должны находиться в приложении PaNa CRM.

### 4.2. Контракт адаптера

Каждый адаптер должен реализовывать единый контракт:

```text
validate_configuration()
get_capabilities()
send_message(message)
normalize_recipient(phone)
parse_delivery_callback(request)
parse_incoming_callback(request)
map_provider_status(provider_status)
```

Методы обработки delivery callback и входящих сообщений могут быть недоступны, если провайдер не поддерживает соответствующую возможность. Это отражается в `get_capabilities()` и не считается ошибкой адаптера.

### 4.3. Реестр возможностей провайдера

Для каждой конфигурации система хранит возможности:

- `outbound_sms`;
- `inbound_sms`;
- `delivery_reports`;
- `sender_name`;
- `owned_sender_number`;
- `two_way_messaging`;
- `multipart_messages`;
- `unicode_messages`.

Интерфейс и workflow должны проверять возможности активной конфигурации. Неподдерживаемые действия скрываются или отображаются как недоступные с понятным объяснением.

## 5. Этапы реализации

### 5.1. Этап 1 — произвольные SMS и история

Цель: предоставить базовый рабочий канал исходящих SMS внутри CRM.

В scope:

- отправка произвольного текста из профиля пациента;
- отправка из конкретного кейса;
- возможность связать сообщение с активной задачей;
- выбор номера пациента, если в профиле несколько номеров;
- предпросмотр получателя, отправителя, длины и количества SMS-частей;
- фиксация сообщения до обращения к провайдеру;
- отображение результата отправки;
- единая история SMS в профиле пациента;
- отображение SMS в общей ленте активностей кейса;
- фильтр истории по направлению, статусу, кейсу и периоду;
- сохранение автора отправки;
- повторная отправка сообщения со статусом `Failed`;
- конфигурация активного провайдера на уровне клиники;
- режим эмуляции для прототипа и тестовой среды;
- аудит изменения конфигурации и действий пользователя.

Не входит в этап 1:

- массовая рекламная рассылка;
- автоматическая отправка по workflow;
- управление согласиями на маркетинговые рассылки;
- приём входящих SMS;
- полноценный чат;
- delivery report, если его не предоставляет выбранный провайдер.

### 5.2. Этап 2 — шаблоны SMS

Цель: стандартизировать повторяющиеся сообщения и подготовить SMS для автоматизаций.

В scope:

- CRUD шаблонов без физического удаления: шаблон можно деактивировать;
- версии шаблонов и журнал изменений;
- область применения: клиника, воронка, этап, услуга, тип события;
- языковая версия шаблона;
- переменные пациента, клиники, врача, процедуры, даты, времени и ссылки;
- предпросмотр результата с реальными данными перед отправкой;
- предупреждение о незаполненных переменных;
- ручная отправка шаблона оператором;
- ограничения ролей на создание, редактирование, активацию и использование;
- подготовка шаблонов для будущих автоматических событий.

Автоматическая отправка по событию допускается только как отдельная согласованная задача с правилами запуска, отмены, повторов и предотвращения дублей.

### 5.3. Этап 3 — полноценная переписка

Цель: объединить входящие и исходящие SMS в коммуникационный поток пациента.

В scope:

- номер, поддерживающий приём SMS;
- webhook для входящих сообщений;
- отображение диалога в рабочем пространстве коммуникаций пациента;
- счётчик непрочитанных сообщений;
- очередь входящих SMS для оператора;
- ответ из существующего треда;
- связь сообщения с пациентом, кейсом и задачей;
- создание нового контакта/кейса, если пациент не найден;
- обработка неоднозначного совпадения;
- синхронизация состояния между Inbox и профилем пациента;
- история ошибок и повторов;
- защита webhook и предотвращение повторной обработки одного события.

## 6. Функциональные требования

### 6.1. Отправка сообщения

1. Пользователь открывает профиль пациента или кейс.
2. Выбирает канал `SMS`.
3. Система подставляет основной мобильный номер пациента.
4. Если доступно несколько номеров, пользователь выбирает один из них.
5. Пользователь вводит произвольный текст или, начиная с этапа 2, выбирает шаблон.
6. Система показывает количество символов и расчётное количество частей.
7. После подтверждения CRM создаёт запись SMS со статусом `Queued`.
8. `SMS Service` выбирает активную конфигурацию для клиники и вызывает соответствующий адаптер.
9. Результат провайдера сохраняется в записи сообщения и в аудите.
10. Сообщение отображается в профиле пациента и связанной истории кейса.

Если у пациента нет валидного номера, кнопка отправки заблокирована, а пользователь получает понятное сообщение с возможностью перейти к редактированию профиля при наличии права.

### 6.2. Выбор провайдера

Порядок выбора:

1. активная конфигурация, назначенная клинике кейса;
2. глобальная конфигурация по умолчанию;
3. режим эмуляции — только в demo/test окружении;
4. ошибка конфигурации, если ни один вариант недоступен.

Автоматическое переключение на резервного провайдера не входит в первый этап. Его можно добавить позже только с правилами, предотвращающими повторную доставку одного сообщения через двух провайдеров.

### 6.3. Входящее сообщение

При получении webhook система:

1. проверяет источник, подпись/секрет и допустимость запроса;
2. проверяет уникальность события;
3. нормализует номер отправителя;
4. ищет контактные идентификаторы с таким номером;
5. автоматически связывает SMS с пациентом только при одном достоверном совпадении;
6. при нескольких совпадениях помещает сообщение в очередь ручного сопоставления для пользователя с соответствующим правом;
7. при отсутствии совпадения создаёт непривязанный входящий контакт, но не создаёт пациента автоматически;
8. отображает сообщение в Inbox и после привязки — в профиле пациента.

Автоматическая привязка по одному нормализованному номеру принята как рекомендуемое правило. Привязка по имени, свободному тексту или частичному совпадению номера без подтверждения администратора запрещена.

## 7. Статусы

| Статус CRM | Значение |
|---|---|
| `Draft` | Сообщение создано, но не подтверждено пользователем. |
| `Queued` | Запись зафиксирована и ожидает вызова провайдера. |
| `Submitted` | Провайдер принял запрос, но доставка не подтверждена. |
| `Delivered` | Доставка подтверждена провайдером. |
| `Failed` | Запрос не принят либо произошла техническая ошибка. |
| `Undelivered` | Провайдер подтвердил невозможность доставки. |
| `Received` | Получено входящее SMS. |
| `Unknown` | Получен неизвестный или не сопоставленный статус. |

Правила:

- оригинальный статус и payload провайдера сохраняются отдельно от нормализованного статуса;
- отсутствие delivery report не является ошибкой;
- если провайдер не поддерживает delivery report, `Submitted` является конечным техническим статусом;
- UI не должен заменять `Submitted` на `Delivered` по таймеру;
- повторная отправка создаёт новую запись SMS, связанную с исходной, а не перезаписывает её.

## 9. Особенности SuperVoIP

- Поддерживаются исходящие SMS через REST API.
- Отправка возможна с номера SuperVoIP, случайного номера 2way, имени отправителя или режима провайдера.
- Для отправки с конкретного номера в REST API используется `sender = voipNumber`, а `voipNumber` содержит идентификатор ресурса вида `/api/voip_numbers/{ID}`, а не отображаемый номер телефона.
- Приём SMS требует мобильного номера SuperVoIP либо подходящего режима 2way.
- Входящие сообщения могут передаваться на URL CRM с номером отправителя, номером получателя и текстом.
- При использовании буквенно-цифрового имени отправителя пациент не сможет ответить в тот же диалог.
- SuperVoIP не предоставляет delivery reports. Поэтому успешный API-ответ отображается как `Submitted`, а не `Delivered`.
- Поддержка польских символов и других Unicode-символов уменьшает объём одной SMS-части; интерфейс должен показывать расчёт частей до отправки.

Источник: https://pomoc.supervoip.pl/5182774319901-usluga-sms/

## 10. Особенности SMSAPI

- Адаптер должен поддерживать исходящую отправку и сохранение ID сообщения провайдера.
- При подключённой услуге входящих сообщений/VMN адаптер обрабатывает входящие callback.
- При наличии delivery callback статусы преобразуются в `Delivered`, `Undelivered` или `Failed`.
- Конкретные sender name, номер и правила входящих сообщений определяются активированными услугами аккаунта, а не предполагаются системой.

## 11. Интерфейс

### 11.1. Профиль пациента

Во вкладке коммуникаций:

- отдельный SMS-тред или канал внутри единого conversation workspace;
- история по всем кейсам пациента с указанием связанного кейса;
- направление, дата, автор и статус каждого сообщения;
- понятное различие `Submitted` и `Delivered`;
- действие `Повторить` только для сообщений с ошибкой и пользователей с правом отправки;
- переход из сообщения к связанному кейсу и задаче.

### 11.2. Карточка кейса

- быстрое действие `SMS`;
- получатель и номер подставляются из профиля пациента;
- новое сообщение автоматически связывается с открытым кейсом;
- пользователь может дополнительно связать сообщение с активной задачей;
- отправка SMS фиксируется как активность, но не закрывает задачу автоматически без отдельного workflow-правила.

### 11.3. Настройки

Администратор видит:

- список конфигураций провайдеров;
- клинику и статус каждой конфигурации;
- подтверждённые возможности;
- безопасную форму credentials без отображения сохранённого секрета;
- проверку подключения;
- отправку тестового сообщения;
- журнал последних технических ошибок;
- управление шаблонами на втором этапе.

## 12. RBAC

Права должны быть атомарными и не привязываться жёстко к названию роли:

| Право | Назначение |
|---|---|
| `sms.read` | Просматривать SMS в доступных пациентских данных. |
| `sms.send_custom` | Отправлять произвольный текст. |
| `sms.send_template` | Отправлять активные шаблоны. |
| `sms.retry` | Повторять неуспешную отправку. |
| `sms.match_patient` | Вручную сопоставлять входящее сообщение с пациентом. |
| `sms.template_manage` | Создавать, редактировать и деактивировать шаблоны. |
| `sms.provider_manage` | Управлять конфигурациями провайдеров. |
| `sms.technical_log_read` | Видеть технические payload и ошибки интеграции. |

Доступ к сообщению дополнительно ограничивается клиникой, кейсом и пациентом, доступными пользователю по общей RBAC-модели CRM.

## 13. Аудит и безопасность

- логировать отправку, повтор, изменение статуса, ручную привязку, отвязку и изменение конфигурации;
- не сохранять API-токены в SMS Message, audit payload или frontend state;
- маскировать credentials в UI и логах;
- обеспечить TLS для API и callback;
- проверять webhook secret/signature, если поддерживается провайдером;
- ограничить частоту callback и отправки;
- хранить raw payload только в техническом журнале с ограниченным RBAC-доступом;
- исключить повторную обработку webhook по event/message ID или вычисленному idempotency key;
- персональные данные и тексты SMS обрабатывать по правилам хранения данных CRM и GDPR.

## 14. Ошибки и повторные попытки

- таймаут или временная ошибка создаёт контролируемую повторную попытку без новой пользовательской отправки;
- количество технических повторов и интервалы задаются конфигурацией backend;
- постоянная ошибка номера, авторизации или sender ID переводит сообщение в `Failed` без бесконечных повторов;
- ручной retry создаёт новую попытку/сообщение и сохраняет связь с исходным;
- UI показывает понятную пользователю причину, а технические детали доступны только пользователям с `sms.technical_log_read`;
- смена провайдера не должна автоматически повторно отправлять ранее не подтверждённые сообщения.

## 15. Нефункциональные требования

- провайдерский API не вызывается из браузера;
- отправка выполняется асинхронно через backend job/queue;
- создание внутренней записи SMS не должно зависеть от доступности провайдера;
- webhook должен быть идемпотентным;
- время появления принятого входящего SMS в CRM: целевое значение до 10 секунд после callback;
- каждое изменение статуса должно быть трассируемым;
- добавление нового исходящего провайдера не требует изменения Patient Profile, Case UI и SMS Message schema;
- отключение провайдера не нарушает чтение исторических сообщений;
- demo/test среда не должна отправлять реальные SMS без явного включения production-конфигурации.

## 16. Критерии приёмки этапа 1

1. Пользователь с правом `sms.send_custom` может отправить произвольное SMS из профиля пациента с валидным мобильным номером.
2. Из карточки кейса сообщение создаётся со ссылкой на пациента и открытый кейс.
3. Сообщение появляется в истории до вызова провайдера и проходит состояния `Queued` → `Submitted` либо `Failed`.
4. При использовании провайдера без delivery reports UI не показывает сообщение как доставленное.
5. При ошибке сообщение остаётся в истории с безопасным описанием причины и доступным действием retry согласно RBAC.
6. Пользователь без права отправки видит историю в пределах своих данных, но не видит активной кнопки отправки.
7. Администратор может создать конфигурацию SMSAPI или SuperVoIP, проверить её и назначить клинике.
8. Смена активной конфигурации не меняет и не скрывает существующую историю.
9. В режиме эмуляции не выполняется внешний API-вызов, но сохраняется реалистичный статус, активность и аудит.
10. Один пользовательский submit не может создать две фактические отправки из-за повторного запроса интерфейса.
11. Токены и пароли провайдера не присутствуют в браузерном state, обычном audit log и данных SMS Message.
12. Отправка SMS не закрывает связанную задачу автоматически, если для этого не настроено отдельное правило workflow.

## 17. Критерии приёмки этапа 2

1. Администратор может создать, изменить и деактивировать шаблон без удаления истории версий.
2. Пользователь видит только шаблоны, доступные для его клиники и контекста.
3. Перед отправкой CRM подставляет значения переменных и показывает финальный текст.
4. Отправка блокируется, если обязательная переменная не заполнена.
5. SMS Message хранит фактически отправленный текст и версию шаблона.
6. Пользователь без `sms.template_manage` не может менять шаблоны.

## 18. Критерии приёмки этапа 3

1. Валидный входящий callback создаёт ровно одно сообщение со статусом `Received`.
2. При одном достоверном совпадении номера SMS автоматически связывается с пациентом.
3. При нескольких совпадениях сообщение попадает в очередь ручного сопоставления и не назначается произвольно.
4. При отсутствии совпадения CRM не создаёт пациента автоматически.
5. Ответ оператора отображается в том же треде и сохраняется как отдельное исходящее SMS.
6. Непрочитанное сообщение отображается в Inbox и профиле пациента согласно RBAC.
7. Повторный callback с тем же идентификатором не создаёт дубликат.
8. При использовании sender name, не поддерживающего ответы, интерфейс предупреждает об отсутствии двустороннего режима.

## 19. Зависимости и решения перед разработкой

### Подтверждено

- этап 1 начинается с произвольных SMS и истории;
- этап 2 добавляет шаблоны;
- этап 3 добавляет полноценную двустороннюю переписку;
- решение должно поддерживать замену SMSAPI на SuperVoIP или другого провайдера;
- в прототипе допустима эмуляция внешней отправки.

### Требует решения владельца продукта

1. Какой провайдер используется первым в production: SMSAPI или SuperVoIP.
2. Какая клиника использует какой sender name/номер.
3. Нужны ли разные конфигурации для Panamedica, Panacomfort и International.
4. Требуется ли маркетинговая массовая рассылка; она не должна автоматически смешиваться с сервисными SMS.
5. Какие сроки хранения текстов SMS и технических payload применяются.
6. Какие роли получают `sms.send_custom`, так как произвольный текст несёт больший операционный риск, чем утверждённый шаблон.

### Техническая проверка перед оценкой этапа 3

- наличие подходящего входящего номера у выбранного провайдера;
- формат, аутентификация и retry-поведение callback;
- возможность однозначно получить provider message/event ID;
- поддерживаемые sender modes на конкретном аккаунте;
- лимиты API и тарифы;
- правила обработки STOP/отказа от коммуникаций, если будут маркетинговые SMS.

## 20. Рекомендуемая декомпозиция разработки

1. Data model: SMS Message и Provider Configuration.
2. Internal SMS Service и capability registry.
3. Emulator Adapter.
4. UI отправки и история в Patient Profile/Case.
5. RBAC, аудит и технический журнал.
6. Первый production adapter: SMSAPI или SuperVoIP.
7. Второй provider adapter и проверка заменяемости.
8. Template module.
9. Inbound webhook, matching queue и Inbox integration.
10. Workflow automation — отдельным согласованным инкрементом.

## 21. Что не следует делать

- не вызывать SMSAPI/SuperVoIP напрямую из React-компонентов;
- не хранить provider-specific поля в основной UI-модели пациента или кейса;
- не считать HTTP 200 подтверждением доставки;
- не перезаписывать историю при retry;
- не создавать пациента автоматически по неизвестному номеру;
- не привязывать сообщение к первому найденному пациенту при дублях;
- не объединять сервисные и маркетинговые согласия без отдельного правила;
- не удалять использованные конфигурации и шаблоны физически;
- не закрывать задачу только по факту отправки SMS без настроенного workflow-правила.
